                                          Summary

         This experiment connects rotation representations, quadrotor actuation and
     geometric control in a ROS trajectory-tracking system. The rotor-allocation analysis
     shows why reversing two propeller configurations removes one independent control
     direction. A body-frame quadratic drag model gives an explicit force-compensation
     term. The implemented controller was evaluated using recorded flight from the
     official Unity/TESSE simulator on a circular reference of radius 5 m. After the
     first two reference periods, the vehicle completed 2.376 observed turns with a three-
     dimensional position RMS error of 0.3063 m and a radial RMS error of 0.0829 m.
     The error decomposition identifies a persistent height offset as the main contributor.
     Separate numerical results illustrate how the specified drag compensation reduces
     tracking error when the plant follows that drag law.



1    Lab Introduction and Team Information
Quadrotor trajectory tracking requires a consistent connection between state coordinates
and motor commands. A correct feedback equation can generate the wrong motion if the
rotation direction, thrust sign or rotor numbering changes between the model and the
simulator. This lab examines that connection through the individual exercises and the
ROS controller implementation specified in MIT VNAV Lab 3 [1].
The report follows the three deliverables: quaternion conversions, modelling and control
analysis, and geometric control of a simulated UAV. The implemented control loop adapts
the geometric approach of Lee et al. [2] to an upward world and body z axis. Its performance
is assessed using measured trajectories, a retained RViz recording and numerical checks of
the shared controller equations.

2.1    Deliverable 1: From attitude messages to control variables
The controller receives the drone’s orientation as a quaternion in a ROS message. Its
feedback equations need a rotation matrix, while the desired heading is specified by a yaw
angle. This exercise explains how to obtain those quantities from the received data.
Three C++ types appear in this process. A geometry_msgs::Quaternion carries the
four components (x, y, z, w) between ROS nodes. A tf2::Quaternion stores the same
rotation in a form supported by the tf2 rotation utilities. An Eigen::Matrix3d stores
the corresponding 3 × 3 rotation matrix for matrix and vector calculations. Converting
between the quaternion and matrix representations preserves the represented orientation;
extracting yaw selects its heading component.

A. Reading and writing quaternion data (A1–A3)

For A1, suppose quat_msg is the received message and quat_tf is an already declared tf2
quaternion. The following call copies the message components into quat_tf [3]:
tf2::fromMsg(quat_msg, quat_tf);

For A2, the reverse operation creates a ROS message from a computed tf2 quaternion.
This is useful when an orientation must be published to another node:
geometry_msgs::Quaternion quat_msg = tf2::toMsg(quat_tf);

These are separate code examples, using the variable names specified in the exercise.
For A3, the scalar component of the quaternion is obtained with:
quat_tf.w();

A quaternion contains a vector part (x, y, z) and a scalar part w. Reading w returns one
stored component. Calculating yaw requires the rotation represented by the quaternion,
as shown next.

B. Obtaining heading and a rotation matrix (B1–B2)

For B1, extract yaw from the tf2 quaternion quat_t with one function call [4]:
double yaw = tf2::getYaw(quat_t);

The result is a heading angle in radians. In this lab, the desired-state callback uses this
operation to obtain ψd from the reference orientation. The controller then uses ψd to
construct its desired heading direction.
For B2, convert a ROS quaternion message into an Eigen quaternion, then convert that
quaternion into a rotation matrix [5]:
Eigen::Quaterniond q_eigen;
tf2::fromMsg(quat_msg, q_eigen);
Eigen::Matrix3d R = q_eigen.toRotationMatrix();

The first line declares storage; the next two lines perform the two requested conversions.
Here the input is assumed to be a unit quaternion. The actual current-state callback
checks the input and normalises it before forming R.
For the current attitude in this lab, R maps a body-frame vector to the world frame:
v w = Rv b . Its transpose performs the reverse conversion. The controller therefore computes
Ω = RT Ωworld to express the received angular velocity in body coordinates. It also uses R
to calculate attitude error and the current thrust direction. Thus yaw extraction supplies
the desired heading, while matrix conversion supplies the current attitude needed by the
feedback equations.

4    Discussion
The allocation proof explains a structural requirement for tracking position and yaw
independently. The original layout provides four independent wrench directions. In the
modified layout, yaw moment is tied to roll moment, so feedback tuning cannot recover
the missing actuation direction. The simulator matrix also shows why rotor numbering
and yaw signs must be checked separately when implementing the controller.
The official flight demonstrates repeated circular motion with bounded error in the recorded
window. Its 0.0829 m radial RMS error is about 1.66% of the reference radius. Height
accounts for 72.1% of the mean squared three-dimensional position error, with a mean
height offset of −0.2532 m. Thus the planar circle and the three-dimensional accuracy
convey different aspects of the result. Evaluating both prevents the top view from obscuring
vertical behaviour.
Several implementation choices are relevant to this offset and the gain sensitivity. The
moment law omits desired angular-rate feedforward, the controller uses the skeleton inertia
approximation, and simulator scheduling holds motor commands between updates. The
available trials change multiple gains simultaneously and do not isolate those mechanisms.
A direct follow-up would compare vertical error with one model or feedforward change at
a time, using the same trajectory and evaluation window.
The drag calculation has a narrower, well-defined purpose: it cancels a specified force
model. The independent numerical runs support that mechanism, reducing RMS error
by 75.6% when the plant includes the same drag law. Applying the term to TESSE
would require checking that its force model is appropriate. The official flight used the
uncompensated controller, and its measured accuracy remains the basis for the simulator
result.
Finally, the error metric uses the most recent received reference at each state callback. It
therefore includes asynchronous reference updates as well as vehicle tracking behaviour.
The 1,495 steady samples are correlated observations from one run; they quantify that
trajectory and do not establish repeatability across runs or initial conditions.


5    Conclusions
The lab links quaternion conversion and rotor allocation to a working ROS geometric
controller. The rank proof identifies the loss of independent yaw authority after reversing
two rotor configurations, while the drag model gives a consistent force correction. The
official TESSE recording contains 2.376 steady-window turns with a position RMS error
of 0.3063 m. Radial tracking and the measured height offset identify the achieved circular
motion and the principal direction for further control refinement.
