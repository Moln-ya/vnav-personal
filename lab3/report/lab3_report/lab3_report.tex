\begin{abstract}
This experiment connects rotation representations, quadrotor actuation and geometric control in a ROS trajectory-tracking system. The rotor-allocation analysis shows why reversing two propeller configurations removes one independent control direction. A body-frame quadratic drag model gives an explicit force-compensation term. The implemented controller was evaluated using recorded flight from the official Unity/TESSE simulator on a circular reference of radius 5 m. After the first two reference periods, the vehicle completed 2.376 observed turns with a three-dimensional position RMS error of 0.3063 m and a radial RMS error of 0.0829 m. The error decomposition identifies a persistent height offset as the main contributor. Separate numerical results illustrate how the specified drag compensation reduces tracking error when the plant follows that drag law.
\end{abstract}

\section{Lab Introduction and Team Information}
Quadrotor trajectory tracking requires a consistent connection between state coordinates and motor commands. A correct feedback equation can generate the wrong motion if the rotation direction, thrust sign or rotor numbering changes between the model and the simulator. This lab examines that connection through the individual exercises and the ROS controller implementation specified in MIT VNAV Lab 3~\citep{vnav}.

The report follows the three deliverables: quaternion conversions, modelling and control analysis, and geometric control of a simulated UAV. The implemented control loop adapts the geometric approach of \citet{lee2010} to an upward world and body $z$ axis. Its performance is assessed using measured trajectories, a retained RViz recording and numerical checks of the shared controller equations.

\section{Individual Work}
\subsection{Deliverable 1: From attitude messages to control variables}
The controller receives the drone's orientation as a quaternion in a ROS message. Its feedback equations need a rotation matrix, while the desired heading is specified by a yaw angle. This exercise explains how to obtain those quantities from the received data.

Three C++ types appear in this process. A \texttt{geometry\_msgs::Quaternion} carries the four components $(x,y,z,w)$ between ROS nodes. A \texttt{tf2::Quaternion} stores the same rotation in a form supported by the tf2 rotation utilities. An \texttt{Eigen::Matrix3d} stores the corresponding $3\times3$ rotation matrix for matrix and vector calculations. Converting between the quaternion and matrix representations preserves the represented orientation; extracting yaw selects its heading component.

\subsubsection*{A. Reading and writing quaternion data (A1--A3)}
For A1, suppose \texttt{quat\_msg} is the received message and \texttt{quat\_tf} is an already declared tf2 quaternion. The following call copies the message components into \texttt{quat\_tf}~\citep{rosgeometry}:
\begin{lstlisting}
tf2::fromMsg(quat_msg, quat_tf);
\end{lstlisting}
For A2, the reverse operation creates a ROS message from a computed tf2 quaternion. This is useful when an orientation must be published to another node:
\begin{lstlisting}
geometry_msgs::Quaternion quat_msg = tf2::toMsg(quat_tf);
\end{lstlisting}
These are separate code examples, using the variable names specified in the exercise.

For A3, the scalar component of the quaternion is obtained with:
\begin{lstlisting}
quat_tf.w();
\end{lstlisting}
A quaternion contains a vector part $(x,y,z)$ and a scalar part $w$. Reading $w$ returns one stored component. Calculating yaw requires the rotation represented by the quaternion, as shown next.

\subsubsection*{B. Obtaining heading and a rotation matrix (B1--B2)}
For B1, extract yaw from the tf2 quaternion \texttt{quat\_t} with one function call~\citep{rosutils}:
\begin{lstlisting}
double yaw = tf2::getYaw(quat_t);
\end{lstlisting}
The result is a heading angle in radians. In this lab, the desired-state callback uses this operation to obtain $\psi_d$ from the reference orientation. The controller then uses $\psi_d$ to construct its desired heading direction.

For B2, convert a ROS quaternion message into an Eigen quaternion, then convert that quaternion into a rotation matrix~\citep{roseigen}:
\begin{lstlisting}
Eigen::Quaterniond q_eigen;
tf2::fromMsg(quat_msg, q_eigen);
Eigen::Matrix3d R = q_eigen.toRotationMatrix();
\end{lstlisting}
The first line declares storage; the next two lines perform the two requested conversions. Here the input is assumed to be a unit quaternion. The actual current-state callback checks the input and normalises it before forming $R$.

For the current attitude in this lab, $R$ maps a body-frame vector to the world frame: $v^w=Rv^b$. Its transpose performs the reverse conversion. The controller therefore computes $\Omega=R^T\Omega_{\mathrm{world}}$ to express the received angular velocity in body coordinates. It also uses $R$ to calculate attitude error and the current thrust direction. Thus yaw extraction supplies the desired heading, while matrix conversion supplies the current attitude needed by the feedback equations.

\subsection{Deliverable 2A: Rotor layout and control authority}
Use the top view in Figure~\ref{fig:rotors}, with $x$ to the right, $y$ upward on the page and $z$ out of the page. Let $d$ be the centre-to-rotor distance, $a=d/\sqrt{2}$, $c_f>0$ the lift coefficient and $c_d>0$ the yaw reaction-torque coefficient. The individual exercise numbers the rotor positions as
\begin{equation}
 \rho_1=(-a,a,0)^T,\quad \rho_2=(-a,-a,0)^T,\quad
 \rho_3=(a,-a,0)^T,\quad \rho_4=(a,a,0)^T.
\end{equation}

\begin{figure}[H]
\centering\includegraphics[width=\linewidth]{figures/rotor_layout.pdf}
\caption{Rotor configurations for the individual exercise. CW and CCW denote rotation viewed from above; the indicated $M_z$ is the resulting body reaction torque. Reversing rotors 3 and 4, with matching propeller types, preserves upward lift and changes the yaw-torque signs. Diagram redrawn from the course configuration~\citep{vnav}.}
\label{fig:rotors}
\end{figure}

Let $u_i=\omega_i^2\geq0$, with $\omega_i$ measured in each rotor's configured lifting direction. The force is $f_i=c_fu_i$, and the moment arm gives
\begin{equation}
 \rho_i\times(0,0,f_i)^T=(\rho_{iy}f_i,-\rho_{ix}f_i,0)^T.
\end{equation}
For the wrench $w=(f,M_x,M_y,M_z)^T$, configuration (a) therefore has
\begin{equation}
 w=F_a u,\qquad
 F_a=\begin{bmatrix}
 c_f&c_f&c_f&c_f\\
 ac_f&-ac_f&-ac_f&ac_f\\
 ac_f&ac_f&-ac_f&-ac_f\\
 -c_d&c_d&-c_d&c_d
 \end{bmatrix}.
 \label{eq:fa}
\end{equation}
After division by their nonzero scale factors, the four rows are mutually orthogonal. Consequently,
\begin{equation}
 \det F_a=16a^2c_f^3c_d=8d^2c_f^3c_d\ne0,
 \qquad \operatorname{rank}(F_a)=4.
\end{equation}
All four wrench components can be adjusted independently near a positive-speed hover, within actuator limits.

For configuration (b), only the last row changes:
\begin{equation}
 F_b=\begin{bmatrix}
 c_f&c_f&c_f&c_f\\
 ac_f&-ac_f&-ac_f&ac_f\\
 ac_f&ac_f&-ac_f&-ac_f\\
 -c_d&c_d&c_d&-c_d
 \end{bmatrix}.
 \label{eq:fb}
\end{equation}
The last row equals $-c_d/(ac_f)$ times the second row. The other three rows remain independent, so
\begin{equation}
 \boxed{\operatorname{rank}(F_b)=3,\qquad M_z=-\frac{c_d}{ac_f}M_x.}
\end{equation}
For example, $F_b(1,-1,1,-1)^T=0$. At level hover with zero angular velocity, holding position while starting a pure yaw rotation requires zero roll moment and a nonzero yaw moment. The constraint above makes that command impossible. Configuration (b) therefore cannot track an arbitrary independently prescribed trajectory $(x,y,z,\Psi)$.

\subsection{Deliverable 2B: Compensation for quadratic body drag}
Let $R\in SO(3)$ map body vectors to world coordinates and let $v$ be world velocity. The drag law in the assignment becomes
\begin{equation}
 v^b=R^Tv,\qquad D=\operatorname{diag}(0.1,0.1,0.2),\qquad
 F_D^b=-D\bigl(v^b\odot|v^b|\bigr),\qquad F_D^w=RF_D^b,
\end{equation}
where $\odot$ denotes componentwise multiplication. Its sign is physically consistent because
\begin{equation}
 (v^b)^TF_D^b=-0.1|v_x^b|^3-0.1|v_y^b|^3-0.2|v_z^b|^3\leq0.
\end{equation}
With $e_3=(0,0,1)^T$ and upward $z$, translation obeys
\begin{equation}
 m\dot v=-mg e_3+fRe_3+F_D^w.
\end{equation}
Define $e_x=x-x_d$ and $e_v=v-v_d$. Subtract the estimated world-frame drag from the commanded force:
\begin{equation}
 \boxed{A=-k_xe_x-k_ve_v+mg e_3+m\ddot x_d-\widehat F_D^w.}
 \label{eq:drag}
\end{equation}
Compute the estimate from measured velocity and attitude, then use this same $A$ for both the desired thrust direction and thrust magnitude. If the attitude follows that direction and the drag estimate is exact, substitution into the dynamics gives $m\dot e_v=-k_xe_x-k_ve_v$. Otherwise, the remaining terms include attitude tracking error and $F_D^w-\widehat F_D^w$.

\begin{figure}[H]
\centering\includegraphics[width=.9\linewidth]{figures/drag_compensation.pdf}
\caption{Recorded compensation comparison in the independent rigid-body model. Each bar is one deterministic run with a 1 ms integration step and the prescribed quadratic drag. RMS error is evaluated after two circular periods. The gains are $(k_x,k_v,k_R,k_\Omega)=(6,4.7,64,16)$. These values come from the retained numerical validation log; no uncertainty interval is estimated.}
\label{fig:drag}
\end{figure}

The numerical comparison in Figure~\ref{fig:drag} reduced the recorded RMS error from 0.08337 m to 0.02033 m, a reduction of 75.6\%. This result supports the compensation mechanism under the specified plant model. The official TESSE flight reported below used compensation disabled, so the two evaluations address different conditions.

\subsection{Deliverable 3: ROS control architecture}
The completed controller closes the loop between the trajectory publisher and the official TESSE simulator through the ROS bridge (Figure~\ref{fig:loop}). Its three interfaces are \texttt{/desired\_state}, \texttt{/current\_state} and \texttt{/rotor\_speed\_cmds}. They carry \texttt{MultiDOFJointTrajectoryPoint}, \texttt{Odometry} and \texttt{Actuators} messages, respectively.

\begin{figure}[H]
\centering\includegraphics[width=\linewidth]{figures/control_loop.pdf}
\caption{Implemented control loop. The desired state supplies position, velocity, acceleration and yaw. The controller converts the received world-frame angular velocity to the body frame, computes thrust and moments, and allocates them to four rotor speeds. The bridge returns the simulated state.}
\label{fig:loop}
\end{figure}

The implementation checks message-array sizes, finite values and quaternion norms before updating the control state. It stores the most recent valid reference and measurement. The final configuration suppresses command publication when either input is more than 1 s old. The timer is configured at 200 Hz; this is a requested control rate, while transport and simulator scheduling determine the actual message rate.

The recorded run used ROS Noetic in an ARM64 container, with the unmodified x86\_64 Unity/TESSE executable running through Box64 0.3.6. The retained build log reports successful compilation of the controller and its dependency packages. The model constants used by the controller are $m=1$ kg, $g=9.81$ m\,s$^{-2}$, $d=0.3$ m, $c_f=10^{-3}$ and $c_d=10^{-5}$, with angular speed in rad\,s$^{-1}$. It retains the skeleton's $J=I_3$ inertia approximation.

\subsection{Geometric feedback and rotor allocation}
For the official flight, the commanded force is Equation~\eqref{eq:drag} without the drag term. The reference heading is $b_{1c}=(\cos\psi_d,\sin\psi_d,0)^T$. The desired attitude follows from
\begin{equation}
 b_{3d}=\frac{A}{\|A\|},\qquad
 b_{2d}=\frac{b_{3d}\times b_{1c}}{\|b_{3d}\times b_{1c}\|},\qquad
 R_d=[\,b_{2d}\times b_{3d}\quad b_{2d}\quad b_{3d}\,].
\end{equation}
The positive $b_{3d}$ sign matches the upward thrust convention. The code handles a near-zero force with a vertical direction and uses a perpendicular heading when the cross product becomes degenerate.

The attitude error, thrust and moment implemented in the controller are
\begin{align}
 e_R&=\tfrac12\bigl(R_d^TR-R^TR_d\bigr)^\vee,\\
 f&=A\cdot Re_3,\\
 M&=-k_R e_R-k_\Omega\Omega+\Omega\times(J\Omega).
 \label{eq:moment}
\end{align}
The vee map returns $(S_{32},S_{13},S_{21})^T$ for a skew-symmetric matrix $S$. The implementation uses the simplifying choice $\Omega_d=\dot\Omega_d=0$ in the attitude feedback law. Although the reference yaw changes with time, its rate is not included as feedforward. The measured angular velocity is transformed as $\Omega=R^T\Omega_{\mathrm{world}}$ before applying Equation~\eqref{eq:moment}.

The simulator uses a different rotor numbering from Equation~\eqref{eq:fa}. Its positions are $(a,a,0)$, $(-a,a,0)$, $(-a,-a,0)$ and $(a,-a,0)$ for rotors 1 to 4. Defining $s_i=\omega_i|\omega_i|$, the implemented map is
\begin{equation}
 \begin{bmatrix}f\\M_x\\M_y\\M_z\end{bmatrix}
 =F_{\mathrm{sim}}s,\qquad
 F_{\mathrm{sim}}=\begin{bmatrix}
 c_f&c_f&c_f&c_f\\
 ac_f&ac_f&-ac_f&-ac_f\\
 -ac_f&ac_f&ac_f&-ac_f\\
 c_d&-c_d&c_d&-c_d
 \end{bmatrix}.
\end{equation}
The inverse is computed once. Each control update obtains $s=F_{\mathrm{sim}}^{-1}w$ and publishes $\omega_i=\operatorname{sign}(s_i)\sqrt{|s_i|}$ in rad\,s$^{-1}$. This signed square root preserves the simulator's reversible input convention.

\subsection{Reference trajectory and evaluation}
The circular reference is
\begin{align}
 x_d(t)&=(5\sin(t/2),\,5\cos(t/2),\,2)^T, & \psi_d(t)&=-t/2,\\
 v_d(t)&=(2.5\cos(t/2),\,-2.5\sin(t/2),\,0)^T,\\
 a_d(t)&=(-1.25\sin(t/2),\,-1.25\cos(t/2),\,0)^T.
\end{align}
It has radius 5 m, speed 2.5 m\,s$^{-1}$ and period $T=4\pi\approx12.566$ s. The retained experiment sequence includes a 25 s stationary test, two circular gain trials and the final recorded circular flight.

The final CSV contains 2,752 state samples over 55.02 s of reference time. At each state callback, the logger pairs the state with the latest received reference. Repeated reference timestamps are therefore retained. The established steady-window rule is $t\geq2T=25.1327$ s, which selects 1,495 samples with reference times from 25.18 to 55.02 s. The first 1,257 samples remain visible in the full-run plots.

For the selected sample set $\mathcal{S}$, the position and radius errors are
\begin{equation}
 E_p=\sqrt{\frac{1}{|\mathcal{S}|}\sum_{i\in\mathcal{S}}\|x_i-x_{d,i}\|^2},\qquad
 E_r=\sqrt{\frac{1}{|\mathcal{S}|}\sum_{i\in\mathcal{S}}
 \left(\sqrt{x_i^2+y_i^2}-5\right)^2}.
\end{equation}
Actual turns are counted using the unwrapped phase $\theta_i=\operatorname{unwrap}(\operatorname{atan2}(x_i,y_i))$, consistent with the sine--cosine reference. The change in phase divided by $2\pi$ measures completed motion independently of the elapsed reference periods. All statistics describe time samples from one flight.

\section{Discussion}
The allocation proof explains a structural requirement for tracking position and yaw independently. The original layout provides four independent wrench directions. In the modified layout, yaw moment is tied to roll moment, so feedback tuning cannot recover the missing actuation direction. The simulator matrix also shows why rotor numbering and yaw signs must be checked separately when implementing the controller.

The official flight demonstrates repeated circular motion with bounded error in the recorded window. Its 0.0829 m radial RMS error is about 1.66\% of the reference radius. Height accounts for 72.1\% of the mean squared three-dimensional position error, with a mean height offset of $-0.2532$ m. Thus the planar circle and the three-dimensional accuracy convey different aspects of the result. Evaluating both prevents the top view from obscuring vertical behaviour.

Several implementation choices are relevant to this offset and the gain sensitivity. The moment law omits desired angular-rate feedforward, the controller uses the skeleton inertia approximation, and simulator scheduling holds motor commands between updates. The available trials change multiple gains simultaneously and do not isolate those mechanisms. A direct follow-up would compare vertical error with one model or feedforward change at a time, using the same trajectory and evaluation window.

The drag calculation has a narrower, well-defined purpose: it cancels a specified force model. The independent numerical runs support that mechanism, reducing RMS error by 75.6\% when the plant includes the same drag law. Applying the term to TESSE would require checking that its force model is appropriate. The official flight used the uncompensated controller, and its measured accuracy remains the basis for the simulator result.

Finally, the error metric uses the most recent received reference at each state callback. It therefore includes asynchronous reference updates as well as vehicle tracking behaviour. The 1,495 steady samples are correlated observations from one run; they quantify that trajectory and do not establish repeatability across runs or initial conditions.

\section{Conclusions}
The lab links quaternion conversion and rotor allocation to a working ROS geometric controller. The rank proof identifies the loss of independent yaw authority after reversing two rotor configurations, while the drag model gives a consistent force correction. The official TESSE recording contains 2.376 steady-window turns with a position RMS error of 0.3063 m. Radial tracking and the measured height offset identify the achieved circular motion and the principal direction for further control refinement.
